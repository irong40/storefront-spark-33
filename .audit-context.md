## What Was Built
Owner order acknowledgment system for imPRESSive Juice Bar (juicebar). When a customer completes checkout, the business owner now receives an email with order details and a "Confirm This Order" button. Clicking it calls a new Supabase edge function (`confirm-order`) that stamps `owner_acknowledged_at` on the order row and returns a branded HTML confirmation page. Unacknowledged pending orders are highlighted amber in the admin orders table.

## Key Decisions

- **UUID as confirmation token**: The `confirm-order` edge function accepts `?token={order.id}` where the order ID is a random UUID v4. We deliberately chose not to generate a separate signed token because: (a) UUID v4 is cryptographically random and effectively unguessable, (b) the link is only sent to a trusted email inbox, (c) adding HMAC tokens would require key management for no practical security gain at this scale.
- **Edge function returns HTML directly**: The confirm URL points to the Supabase edge function endpoint rather than a React route. This keeps the happy path to a single HTTP request with no client-side JS dependency — the owner can tap from Gmail on mobile and see a result immediately.
- **GET method for confirmation**: Email clients occasionally pre-fetch links for preview/spam scoring, which could trigger false confirmations. This is a known tradeoff accepted for simplicity at juice-bar scale. Mitigation: the function is idempotent (second click shows "already confirmed"), and a false positive is recoverable (admin can track status changes).
- **Owner email failure is non-fatal**: The owner alert is wrapped in try/catch — a Resend failure on the owner email does not fail the customer confirmation response. This is intentional; customer UX takes priority.
- **Owner email address via env var**: `OWNER_EMAIL` env var defaults to `info@impressivejb.com` if not set. This avoids hardcoding in edge function source.
- **Admin table indicator**: Only `status === 'pending'` AND `owner_acknowledged_at === null` rows are flagged. Orders in other statuses (confirmed, preparing, etc.) are not flagged even if unacknowledged — the status change itself implies the owner acted.

## Areas of Concern

1. **Pre-fetch false confirmation (GET semantics)**: Some email security gateways follow all links in emails to check for malware. This would silently acknowledge an order before the owner sees it. The mitigations are weak (idempotent stamp, not a real guard). A POST-based flow (button submits a form) would be more correct but requires JS or a two-step HTML form.
2. **No expiry on confirmation token**: The token (order UUID) never expires. An owner could click a weeks-old link and "confirm" a completed or archived order. The function doesn't check whether the order is already in a terminal state before writing `owner_acknowledged_at`.
3. **SUPABASE_URL in confirm link**: The owner email embeds `${SUPABASE_URL}/functions/v1/confirm-order?token=...`. If the project URL changes (migration to new org), old emails become dead links. This is acceptable for production but should be noted.
4. **Owner email HTML construction**: The owner email HTML is built inline in `send-order-confirmation/index.ts`. It's not a separate template — a second large HTML block in an already large function. Maintainability concern if the email template grows.
5. **No RLS on `owner_acknowledged_at` writes**: The `confirm-order` function uses the service role key, bypassing RLS. This is appropriate for an edge function but means any caller with a valid order UUID can stamp the field. There's no admin-only restriction.

## Testing Status

- **No automated tests**: This project has no test suite. Changes were manually reviewed for TypeScript correctness (`tsc --noEmit` passed clean).
- **Edge functions untested locally**: Supabase edge functions require `supabase functions serve` + Deno runtime to test locally. The `confirm-order` function logic is straightforward (read → check → update → return HTML) but has not been executed.
- **Email flow untested**: The full end-to-end (checkout → owner email → confirm tap → DB stamp → admin table refresh) has not been exercised against a live environment.
- **Not covered**: Concurrent confirmations (two taps at once), malformed UUIDs in the token param, Resend API failures mid-flight.

## Known Limitations

- No SMS notification (owner must have email access to acknowledge)
- No push notification / real-time alert if admin tab is already open
- No timeout enforcement — unacknowledged orders have no automated escalation beyond the amber highlight in the UI
- Confirmation link does not embed the admin dashboard URL (owner has to navigate there separately after confirming)
